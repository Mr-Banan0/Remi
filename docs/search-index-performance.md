# Search 索引与缓存：实现和验收

## 范围

本次在 b5e4da6 基础上完成请求内分词复用、持久化增量关键词索引、候选正文按需读取和进程内有界记录缓存。文本模型、连边规则、召回预算与重排提示词保持原样。第四步评估结论为继续使用单 worker 本地缓存；当前没有引入 Redis。

向量仍由 SQLite 对可见候选执行精确余弦距离计算。原有 search_documents.vector 随文档写入更新；本次重点避免向 Python 全量解码向量。ANN 会改变候选集合，需单独验证后才能替换。

## 索引及迁移

`search_lexical` 是 FTS5 派生索引，`search_lexical_vocab` 是词频读取虚拟表，SQLite 另行管理 FTS 影子表。索引记录使用现有分词器产生的词项，以 UTF-8 十六进制编码防止 FTS 再次改变分词。评分沿用原 BM25 公式，统计范围为调用者提供的可见候选池。

既有六张业务表继续保存完整原文、修订、图和索引文档。显式迁移命令：

```sh
.venv/bin/remi index-db --path /path/to/test-copy.sqlite3 --allow-create-schema
```

本次只在临时复制库和测试库创建索引，原 Golden 数据库保持原样。应用启动只检测索引存在性；未迁移库保持原有检索路径。此兼容分支用于部署迁移窗口，所有业务库完成迁移及回归后再删除。

索引新增、更新、删除与业务文档在同一事务内完成；按原表 rowid 定位派生索引行。重建可重复执行并保持业务记录不变。应用写入统一经过 SQLiteStore；外部直接修改 search_documents 的 SQL 写入需随后重建索引。

## 读取与缓存

Search 首先获取文档 ID、来源、记忆和修订 ID、时间等轻量字段。正文、证据结构和向量在候选实际使用时加载。索引首次查询覆盖全部允许的冷、热记录。

跨请求记录缓存以表名、用户 ID、记录 ID 为键，最多 2,048 项、8 MiB 序列化载荷预算，采用 LRU 淘汰。Python 对象管理开销另计。返回值重新解码，调用者修改返回对象不会污染缓存。

本连接写入或删除时移除对应缓存；事务回滚时清空；其他连接提交后通过 PRAGMA data_version 清空。缓存保存原始记录，历史可见性继续由每次查询的时间边界判断。服务关闭时释放缓存。

请求内分词缓存另有 4,096 项和字符／词项预算，请求退出（含异常）后释放。

## 回归证据

最终全量离线测试：541 项通过，1 项原有 Starlette 弃用警告。

- 新增索引测试覆盖多语言词项、子集统计、延迟加载、增删改、回滚、迁移权限、幂等重建、旧连接迁移感知、用户隔离、外部连接失效、调用方修改隔离和容量淘汰。
- 原 V85 Golden 的 13 道主问题与 3 道生命周期查询均使用各自查询时点的数据库副本。
- 与 b5e4da6 运行时代码相比，16/16 返回内容、Planner 输入、Jev 输入和语义 trace 一致；trace 中无语义顺序的 revision_paths 按内容排序后比较。
- 回放固定原 Planner 决策，使用确定性合成向量与重排分数，验证完整程序链路等价性。这些结果不替代真实供应商 Golden 的 R@10、MRR 指标。
- 合成规模实验中，1,000 条文档的词法评分从约 23.3 ms 降至 1.36 ms；10,000 条从约 242 ms 降至 12.5 ms。两种规模得分完全一致，索引评分阶段加载完整文档数均为 0。这里只测稀疏词匹配阶段，数值不代表端到端 Search。

结构化结果见 `search-index-regression.json`。`scripts/check_indexed_search.py` 支持使用指定运行时重放查询快照并输出完整响应与模型输入，输出文件必须为新路径。

## 长期性能边界与 Redis 决定

本次移除了反复分词和全部向量向 Python 解码的主要浪费。可见性元数据、图候选构造与精确向量评分仍有随历史规模增长的工作量，当前并未实现固定成本或全量 ANN 搜索。Add 的记忆候选召回仍保留既有维护规则。

当前单 worker 下，进程内缓存能够避免额外网络跳转。多实例部署、缓存命中率及数据库读取耗时证明共享缓存有收益时，再评估 Redis。届时需维持用户隔离、版本／时间可见性和跨实例失效协议；缓存不可用时仍从持久层读取。
