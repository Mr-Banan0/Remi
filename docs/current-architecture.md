# Remi G10：候选、主体对齐与局部事件维护

当前链路为 GPT 提出候选 → 程序对齐名称并召回 → GPT 逐项定稿 → 程序验证、投影和原子提交。使用 gpt-4o-mini。普通有内容单元两次 GPT，空候选一次，两阶段共享最多一次输出修正；供应商瞬时故障每次调用最多重试一次。Add 默认 180 秒，Search 45 秒。外部模型和向量调用在事务外执行。

## 记录与职责

| 记录 | 内容与维护方式 |
| --- | --- |
| Source 原文 | 完整文本、说话者、消息时间、接收时间和会话；来源由程序保存，模型选择来源 ID，程序复制证据 |
| GraphObject 统一主体 | 人、动物、组织、地点、设备等共用一种身份；程序按同用户、知识时间下的精确名称或已确认别名复用 ID，歧义名称保留待定 |
| relation 关系／状态卡 | 一条独立命题，保留原意、否定、情境和表达模式；本轮支持新增和保持，原卡持续保留为有来源、有观察日期的陈述 |
| event 事件卡 | 一次独立发生或计划；稳定 ID、内容、主体连接、模式、情境、状态、计划日期和实际日期 |
| Revision 修订 | 每次新增或局部变更的来源与字段快照；事件修订通过 revises 追溯 |

持续偏好、关系、状态与事件分别保存。关系具体含义在完整命题与原文中表达。图提供主体→卡片的导航：卡片经 mentions 连接统一主体，修订经 supported_by 连接来源，经 revises 连接前版。主体与卡片各自有 ID；同一主体可连接多张独立关系或事件卡。

本轮把关系类别、主客体方向、开放角色和属性字典、主体生命周期、跨记忆语义边的联合生成职责移出生产合同。具体语义继续保存在卡片与证据中。自动归并同义主体、改名、关系替换／结束、完成事件的日期纠错和跨事件因果维护保留为尚未实现的能力。

## 输入输出与约束

1. **保存输入**：接收用户、请求、会话与消息，输出不可变 Source、请求指纹、连续文本窗口、单元检查点。相同请求内容复用已完成结果，冲突请求返回 409。
2. **提出候选**：GPT 读取本单元原文与至多三段解释上下文，输出独立命题、用户参与情况（involved／not_involved／uncertain）、其他主体的原文名称和来源 ID。程序为每项分配候选 ID；保留含当前用户来源的候选，单独审计仅复述旧上下文的候选。可以独立变化的命题分别提出，日期与暂时状态先保留在候选内容中。程序校验来源范围并复制证据，按参与标志生成唯一的 user 引用，记录模型遗漏或多写引用的情况。其他名称通过引用原文的字面边界检测；出现缺口时使用现有共享修正额度，修正后仍有缺口的候选按身份待定处理。候选协议失败使用共享修正额度，仍无法获得合法候选计划时保留原文与请求检查点，返回可重试错误。
3. **身份与历史召回**：程序按精确原名／已确认别名绑定统一主体，限定用户和知识时间。user 对应 API 用户，每用户分区使用一个稳定 ID；来源的作者身份与命题的参与者分别表达。其余主体提供局部召回入口；每候选取至多六项主体关联卡和两项全局卡，多候选轮流分配至多八张历史卡。完整证据优先保留，超过约 32 KB 时逐张移除低排名历史卡。输出历史内容、来源、状态、日期和 patchable 标志；主体绑定由程序缓存和审计，resolved_subjects 提供给维护阶段复核。
4. **维护定稿**：GPT 每候选选择一次操作。create 生成一张 relation/event 卡；keep 选择已有卡；patch_event 选择历史中标记可修改的事件；pending 保存尚待确定的候选。新增卡片再次判断当前用户是否参与最终命题。候选已明确归属时，两阶段保持一致后生成 user 连接；相反判断使用共享额度复核，仍有冲突时进入 pending。候选参与情况原先为 uncertain 时，维护阶段可根据原文定稿。所有判断差异记入审计，其余已对齐主体持续保留。keep 核对目标原卡与候选归属；事件补丁继承原主体和参与标志。模式区分 asserted、desired、requested、hypothetical、document。情境有原文支持时填写，未指定时由程序记 source_reported。
5. **局部验证**：仅明确陈述、状态为 planned 的既有事件支持补丁。reschedule 更新计划日期；complete 更新发生状态和实际日期；cancel 更新取消状态。补丁保留内容、主体、模式、情境及其余日期。content 保存首次描述；模型仍可能在首次描述中包含旧日期，日期与生命周期的当前值以独立字段为准。完成日期未知时 event_at 保持未知，已有 planned_at 独立保留。一次新的发生通过 create 获得新 ID。来源支持时间按消息时钟解析，消息时间缺省时使用首次保存的接收时间。
6. **候选处置**：模型输出的缺项、重复、非法目标、越权改写、无来源日期等按候选记录原因。共享的一次维护修正只处理失败候选，保留通过项。剩余失败项转 pending。同一目标的冲突补丁共同待定，相同补丁合并为一次修订。未指定时间与无依据的具体时间分别验收。
7. **提交**：程序生成 ID、修订、证据与图边，核对参与标志、主体 ID、user 节点、mentions 边及所有权一致后，准备检索文档与向量，核对召回时目标修订与提交前完整记录后将主体、记忆、边、索引和单元应用检查点一起提交。请求级原文与阶段输出支持故障后重试。待定候选仅形成检索提示，其原始来源参与搜索；它们不进入已确认卡片、图连接或背景视图。

## 查询与背景

Search 保留 BM25＋向量混合召回、一次 GPT 决策、最多两步补搜、Jev 重排、相邻来源和原文字节预算。图仅做主体关联卡的一层有界导航，默认最多十二项。user 提供身份绑定，其余主体提供局部图入口；用户枢纽通过全局检索参与召回，局部扩展保持原有预算。

背景视图选择有来源的 asserted 关系／状态陈述，输出明确标记 source_reported、observed_at、source_ids。关系卡采用追加保存；背景中的陈述表示当时的表达，当前是否仍成立需结合日期、原文条件和后续证据判断。情境化、时限化、互相冲突的状态尚无自动维护能力。待定提示、愿望、请求、假设和文档内容保留各自模式，并通过原文检索读取。

## 存储与实验边界

继续使用 sources、memories、objects、edges、requests、search_documents 六张物理表。记录 schema_version=11，当前检查点 pipeline=G10-user-identity-v8。旧实验代码和数据库独立保存；当前启动遇到旧版主体／记忆 JSON 时要求从原文重放。G09 的复杂生产合同已被本轮局部合同替代。

生产模块只读取 API 输入、当前用户记忆、程序配置和供应商响应。评测文件、问题、答案、人名和场景列表留在测试／实验侧。规则围绕来源、身份、版本、日期与操作权限制定。独立语义小样冻结后记录代码和输入指纹，期望结果由验收器读取，MemoryEngine 仅接收用户文本、时间和请求身份。

离线合同、真实语义维护、图完整性、召回质量与延迟分别验收。真实小样通过后，冻结同一运行版本，再使用 Golden 作为回归衡量。Golden 答案与 bad case 措辞不进入生产逻辑。


## 历史 Golden 与当前验证

2026-10-20：独立语义序列通过 1/4，原有歧义处理问题保留。随后按用户明确指令，冻结同一 G10 V5 完成 Golden；R@10=74.36%，主集逻辑 Add 平均 28.54 秒。130/279 候选进入待定，其中 124 个候选有身份对齐问题；主集正式记录为 106 条关系／状态、2 个事件。该结果反映当前模型输出与身份、分类合同的实际衔接边界。生命周期实际事件修订通过，原文召回和整体语义维护分别验收。详情见 [G10 Golden 与实际图](golden-g10-results.md)。
