# V27：主体、关系与普通记忆共用召回

## 目标与当前链路

原文先经过一次共用召回，模型分别维护主体／关系与普通记忆。候选包含旧主体、显式关系、事件和 fact，并携带来源。模型依据原文、上下文与这些候选作出身份和关系决策。

1. 保存 Source 和请求检查点，按用户文本分处理单元。
2. 共用召回读取当前用户在消息知识时间可见的记录。原文及解释上下文做混合检索，名称／别名提供身份线索，旧卡参与者和一层显式联系补齐关联记录。
3. 合并为一份候选快照：subject_catalog、relation_catalog、history。最多 8 张历史卡、24 个主体，候选包最多 24,000 字节。每张保留卡维持全部主体与来源。预算跳过记录进入 trace。
4. 主体模型直接从原文提出本轮 ref、主体变更、只读绑定与联系操作。共用 history 的事件／fact 提供旧身份语境；最终操作由模型判断。
5. 程序验证归属、引用、证据、主体范围与关系方向，分配新 ID，固定参与者 ref。
6. 普通候选模型从当前原文提出事件／fact 等候选，使用固定 ref 和共用历史解释回指。
7. 普通维护模型对候选与同一批 history 做 create、keep、patch_event、pending 决策。程序附加固定身份映射并执行验证。
8. 校验并发快照，原子提交主体、记忆、修订、图和索引。

relation_catalog 是同一 history 中显式联系的视图；事件／fact 被召回后，其参与者进入主体目录。只提到联系一端时，召回的一层联系携带另一端主体。名称命中和图连接产生候选，身份相同与否由模型依据证据决定。

## 完成标准与验证边界

离线全量 **289 passed、0 skipped、13.11 秒**。新增 9 项覆盖：未点名主体从旧 fact 带回、单端关系带回另一端、三个模型阶段共用快照、事件与无主体 fact、用户与时间隔离、候选预算与参与者闭包、故障续跑、主体与普通候选的 HTTP JSON 载荷。

普通事件生命周期、并发冲突、来源证据、索引与已有六表持久化回归继续通过。新增测试使用独立合成原文和模拟供应商，验证程序合同。该版本真实模型实验与 Golden 尚未运行；V26 的历史语义成绩继续归属 V26。

共用召回使用原文作为检索入口，多个主题会共享有限候选额度。真实检索覆盖率、模型能否正确利用事件／fact 判断主体、整体延迟需要单独实测；离线通过代表程序合同验收通过。
