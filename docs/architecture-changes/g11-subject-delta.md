# G11 V19：候选驱动的主体与关系增量

主体阶段读取候选及其原文证据、同用户可见的旧主体和旧关系。模型选择本轮实际需要新建或更新的内容；程序复制名称、描述词、联系端点和原文。

| 部分 | 处理 |
| --- | --- |
| 保留 | 三阶段、gpt-4o-mini、完整来源、统一主体、来源别名、消息时钟、六表、原子提交、阶段恢复和一次共享修正 |
| 修改 | 每个提及的完整裁决 → 按同一身份分组的稀疏补丁；原文联系重写 → 选择已有候选 ID |
| 新增 | 简短只读绑定；同一联系的来源修订；主体未对齐时由程序保存待定并跳过相应记忆模型工作 |
| 退出 | 第二次抽取、主体阶段补提名称／联系、same_as 引用链、每 ref 的来源／别名／理由复写、隐式补入 @user |
| 调用 | 有可维护记忆时默认三次；纯主体／联系及全部身份待定时两次；空候选一次；共享最多一次输出修正 |
| 边界 | 第一阶段负责候选完整性和来源归属；模型负责候选身份与联系语义；程序校验字面、权限、引用、端点及版本 |

## 第二阶段合同

输入主体候选保留 ref、名字、别名／描述词、同批身份线索和 Source IDs。联系候选带 ID、两个 ref、当前 Source、原文摘录及模式。相关旧主体提供身份和来源别名，旧联系提供 ID、端点及内容。其他独立记忆候选留给第三阶段。

输出有两组修改和一组只读对齐结果：

```json
{
  "subjects": [
    {"operation": "create", "subject_refs": [0, 1], "target_id": null},
    {"operation": "update", "subject_refs": [2], "target_id": "E1"}
  ],
  "connections": [
    {"candidate_id": "c0", "operation": "create", "target_id": null}
  ],
  "bindings": [
    {"subject_refs": [3], "target_id": "E2"}
  ]
}
```

subjects 选择本轮新增／更新的主体，分组 refs 表示同一身份。程序分配新 ID，并保存所选候选中已经过字面来源校验的名字、别名和描述词。update 合并到选定旧主体。

connections 只选择第一阶段提供的联系。create 创建关系卡；update 选择同一对主体、同一表达模式、同一联系命题的旧卡，并追加修订。旧修订和来源继续保存。另一项联系命题创建独立卡。

bindings 仅选择无需修改的已有主体，供联系和记忆绑定参与者。空修改列表表示无修改。未选择的候选保留未对齐状态，程序据此保存相关记忆的待定原因。程序持续检查候选 ID、重复选择、所有权、原文证据、联系端点、修订与快照。

修正共享原有一次预算。有效主体及联系固定，失败独立项可以补交。模型调用在事务外执行，主体、关系、独立记忆、图边、索引和应用检查点在准备完成后原子提交。

## 实验口径

pipeline=`G11-subject-delta-v19`，物理表与 JSON schema_version=12 保持现有布局。旧 pipeline 的未完成请求使用来源重放进入新链路。

主体对比沿用 V18 的 14 组合成用例，事件沿用原五步生命周期。这些用例已参与开发，按回归结果报告。生产代码读取 API 输入、当前用户状态及供应商响应；测试人物、期望、问题和答案保留在实验侧。本轮验证结果见 [主体维护验证](../subject-memory-validation.md)。
