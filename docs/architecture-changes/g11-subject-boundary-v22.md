# V22：限定主体边界

## 定义

主体是原文语境中具有特定身份的人、动物，以及组织或团队。名称和上下文都可以指认主体；具体的“我的姐姐”“邻居家的那只狗”可作为原文称呼。泛指的人群、职业和物种作为描述内容。引用、文档及虚构语境中的具体人物保留各自身份与来源。

保存的主体类型为 person、animal、organization。公司、机构、团队、研究组、俱乐部统一使用 organization；具体类别保留为来源描述词。个人与所属组织保持独立身份，由联系卡表达成员等关系。

设备、地点、建筑、项目、任务、作品和抽象概念进入普通记忆内容。机构身份与建筑位置按语义分别处理；项目团队进入主体层，项目事项进入记忆内容。设备专属生命周期等策略继续属于后续 event／fact 维护范围。

## 链路

1. **提候选与判断范围**：第一次调用沿用 statements／items，同时输出简短 scopes=[{name,kind}]。kind 包含 person、animal、organization、other；other 是候选的范围判断结果。@user 固定为 person，别名可继承同一主体的类型。
2. **程序分流**：前三类生成主体 ref；other 保留在普通记忆内容中。程序剥离 item 中的非主体参与者，将涉及 other 的联系转为普通记忆候选；范围外命名缺少独立内容时保留当前完整来源候选。仅历史引用不会产生当前事实。所有原文持续保留。
3. **召回身份**：名称／别名召回同时检查类型。catalog 提供已有 kind，同名的人、动物和组织保持各自身份候选。跨类型 identity 提示被拦截。
4. **维护主体与联系**：第二次调用继续输出稀疏 subjects／bindings／connections。类型由候选携带，模型专注身份分组和维护；程序检查同组类型一致、更新／绑定目标类型一致、用户 person 身份、引用与联系端点。
5. **维护普通记忆**：保留第三阶段、已有状态卡与事件局部修改。其他事物的名称、别名、关系含义留在内容中；有效无主体 fact 使用空 subject_refs。已提出而未确认的主体继续保持待定。
6. **提交**：保留来源、权限、引用、快照和图边校验，主体、记忆、索引与应用检查点原子提交。

普通有独立记忆单元仍为三个逻辑调用，三个阶段共享最多一次输出修正。纯主体／联系跳过记忆维护；空候选只调用提取。网络重试独立统计。

## 收敛与存储

GraphObject.kind 使用三个允许值。other 仅存在于提取分类及分流记录；主体表只保存 person／animal／organization。旧设备主体示例替换为动物别名和设备 fact 示例。

JSON 记录的其余字段和 schema_version=12 保持；pipeline 为 G11-subject-boundary-v22。六张物理表保持。含旧 kind=entity 等宽泛主体的库在启动时明确要求按原文重放。本轮使用新临时库，历史实验库保持原状并使用各自冻结运行时。

## 开发取舍与验证边界

开发时先尝试在 statement 中重复声明类型，真实输出出现声明遗漏和整体抽取退步。随后尝试只在主体维护补丁中确认三种类型，20 组完整通过 6 组；相机、街道和项目仍被错误归为 organization。最终采用提取阶段的显式 other 分类和程序分流，使模型能够表达范围外候选；主体维护继续使用原有稀疏补丁。

两次早期运行提前停止并保留冻结代码。维护阶段分类方案完整结果保存在 compact-real；显式分类方案分别保留 scope-six 与最终 scoped-real。全部结果按代码指纹区分。

离线测试覆盖类型合同、缺少分类、用户类型、跨类型身份提示、分组／复用类型冲突、同名不同类型、来源归属、范围外候选转为普通内容、无主体 fact、上下文引用及旧库保护。真实测试期望只进入实验驱动。

核心边界和完整记忆链路分别验收。范围外事物未进入主体表，不等于其 fact 已结构化保存；第三阶段仍可能错误输出 pending。待定候选及原文保持可检索，这部分单独记录为记忆维护问题。

具体词所指的真实类型仍由模型结合来源判断；程序负责执行分类、校验合同和引用一致性。最终指标见主体维护验证记录。
