# V43 持续记忆维护闭环

日期：2026-10-26。入口：experiments.subject_engine.SubjectGraphEngine。pipeline：G11-memory-closed-loop-v43。

## 范围与调用预算

保留主体优先、当前原文与一个上下文、来源校验、修订、幂等请求、并发快照检查、原子提交及既有六集合。生产 API V32 继续保持原路径。

每个文本单元正常两个模型调用；主体与记忆共享一次协议修正。模型通过 recall_query、items=[] 请求一次补充检索，再执行一次记忆决策。一次维护最多四次逻辑调用。供应商网络重试、并发重算单列。

每次 Add 最多选两条相关待定，重审各自沿用上述预算，共用 Add 截止时间。单文本请求含两条重审时上限为十二次逻辑调用；正常无待定、无补搜、无修正时为两次。trace 标明 pending_recovery 和 supplement。这里的数量是程序上限，实际成本尚需真实模型验证。

## 已确认的下一版程序补搜方案（尚未实现）

主体阶段先确认并固定本轮 scope。初始记忆候选只来自与已确认主体相交的记忆；同时涉及其他主体的共同记忆可以进入候选，检索范围不沿共同参与者继续扩展。只绑定其他主体的记忆保持在本轮 Add scope 之外。没有确认主体时，主体候选集合为空。

程序使用当前原文和最近一条上下文检索主体范围内的候选，并以正文关键词覆盖、可选向量相似度、时间与事项表达等通用信号计算召回置信度。主体相交用于过滤，不作为相关性加分。当前 BM25 的参与者固定加分不直接用作阈值；不同候选集合的原始分数也不直接比较。

主体候选置信度不足时，程序检索未绑定主体的记忆，将两组候选放入同一个集合，以统一评分器重新排序。无主体候选达到最低相关性并进入最终排名时才提供给记忆模型。程序补搜改变候选深度与候选来源，不改变已经固定的主体 scope，也不引入只属于其他主体的记忆。

记忆模型只接收程序整理后的最终候选，一次完成 create／update／keep／pending 判断。补搜判定与查询由程序负责，模型输出中的 recall_query 在该方案实施时退出。正常调用预算为主体模型一次、记忆模型一次；补搜不增加模型调用，共享协议修正按需增加一次，因此单文本正常为两次、含修正最多三次。

相关性阈值通过 Golden 证据召回实验确定。阈值实验分别报告已核对主体 scope 与模型实际主体 scope：前者隔离召回阈值效果，后者衡量主体错误在完整链路中的影响。阈值只使用通用相关性信号，开发样本和留出样本分开评估。

## 输入与输出

| 环节 | 输入 | 输出 |
| --- | --- | --- |
| 主体维护 | 原文、上一条上下文、名称／别名优先的候选及依据 | 固定主体 ID、未确认指代、别名／描述与主体联系 |
| 双路召回 | 本轮身份、原文和上下文 | 主体关联与无主体候选交替入选，最多六张完整卡 |
| 补充召回 | 模型给出的内容查询 | 保留原六张，放宽主体过滤，合计最多八张，24000 字节 |
| 记忆维护 | 固定身份、历史卡和原文依据 | 四类记忆的创建、更新、保持、待定；字段、参与者、时间、关联的变更 |
| 校验／提交 | 维护计划、原始快照 | 来源和引用校验、并发检查，原子保存主体、记忆、图、索引及检查点 |
| 待定重审 | 相关旧待定原文、本次澄清 | 再次主体维护、记忆维护；成功后记录正式记忆 ID 并清理待定检索提示 |
| 查询 | 全局混合检索种子、有效图 | 主体扩展和事件两跳扩展，再合并排序及证据包装 |

补充召回与主召回都受完整证据卡字节预算约束；超大证据卡会记录为跳过。主体候选仍使用既有关键词策略，未被召回的主体 ID 仍属于候选覆盖边界。

## 统一维护合同

- operation：create／update／keep／pending。update 和 keep 选择同类型的已召回记忆。
- changed_fields：明确修改字段；更新包含完整可读正文。相同目标每轮合并为一项更新。
- participant_mode：retain／add／remove／replace；增减基于旧参与者集合，按需选择当前 P 身份。
- time_updates：最多两个独立字段 planned_at／event_at，各自保留表达、来源、锚点、值与精度。明确撤销使用 expression=null。
- related_memory_ids 增加事件联系；removed_related_memory_ids 撤销已存在联系。两者都需要当前原文依据。
- 事实、偏好、经验保留适用条件和时间范围。同一命题同一范围可以更新；不同成立条件可以各自建卡。
- keep 保留既有记忆，当前陈述与判定保存在原文和请求记录中。

旧 time_field 单时间选择协议已由 time_updates 替代。共享 Candidate 的内部 time_expression 投影固定为 null；生产 V32 仍有该字段的真实调用方，生产合同随服务迁移处理。

## 待定回收与时间

待定候选仍保存在请求检查点及检索提示。每次 Add 在同用户、同会话范围内，按当前内容相关性选择最多两条；上一条原文对应的待定也可进入候选，支持无关键词交集的澄清。每条只重审指定候选，已通过的同来源其他记忆保持原结果。

重审将旧原文作为 CURRENT SOURCE，将本次澄清作为 SUPPORTING CONTEXT。主体候选与旧记忆可见性采用澄清时间；相对日期解析继续采用旧原文的消息时间。正式记忆和新身份依据的观察时间采用澄清时间，来源保留旧原文和澄清。恢复出的主体联系也附加澄清依据。

成功提交同步记录 requests 中唯一 pending_ 解决标记，指向正式记忆，并删除原 doc_pending_ 提示。再次请求和并发重审检查该标记。仍不确定时保留原待定；遇到后续相关输入可再次重审。重审模型输出、主体决策及补搜结果持久化，网络中断复用已完成的阶段。

当前自动重审范围是同会话、有新增相关输入、每次最多两条；跨会话和长期积压全量扫描尚未启用。

## 历史补录与投影

Revision.maintenance_patch 保存当时模型选择的变更字段、原始正文、参与者操作、时间值、原始来源、关联增减及原目标版本。正常更新保持完整可读快照；补录导致版本分支时，程序按来源时间回放明确字段，并用带日期的原始叙述组合正文。

结构化状态、参与者和日期按后续显式变更覆盖；历史有效细节的原文仍可从当前叙述与来源访问。正文中的复杂语义矛盾继续交给模型判断。这版实现提供完整的时间线证据，不把自然语言片段自动改写成一段无时间标记的最新摘要。

重建后同步图边及检索文档。旧持久修订缺少 patch 时，依据其 replaces_revision_id 与旧快照差异恢复操作，这是存量读取兼容，原始证据继续保留。

## 检索与预算

事件相关边按当前查询时间选择有效修订，双向扩展最多两跳、24 个事件节点，去重并检查目标事件可见性。撤销后当前图停止遍历该边；历史时间查询仍可遍历旧边。事件边是导航关联，其具体含义由原文与记忆内容解释。
