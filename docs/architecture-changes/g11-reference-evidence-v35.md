# V35：当前回指与历史身份依据分离

日期：2026-10-22。实验 pipeline：`G11-reference-evidence-v35`。本次用户授权修复主体回指校验，并用 DeepSeek 与 GPT‑4o‑mini 跑完整 Golden。生产服务入口继续运行 V32；本次完整实验由 `SubjectGraphEngine` 执行，共用生产的记忆物化、日期规则、检索和重排方法。

## 修复的问题

历史主体可能以完整描述被保存，例如“a nurse named Nera”；当前输入使用“The nurse”回指。模型选对主体 ID 后，程序需要核对当前提及、历史身份依据与所选 ID 的对应关系。旧校验要求当前引文包含完整旧名或旧描述，会拒绝这种合理回指。

V35 为复用身份增加 `reference`，把本轮表达与历史依据分别表示：

```json
{
  "operation": "reuse",
  "target_id": "E2",
  "reference": {
    "source_id": "S3",
    "mention": "The nurse",
    "basis_id": "B4"
  }
}
```

S/E 是模型请求内的来源／主体编号，B 是本次请求的身份依据编号；程序负责转换回真实 ID。B4 指向 E2 的一条可见名字或描述及其原文。程序保留用户、时间与来源归属信息，模型输入继续使用固定规则、分区文本与独立英文 few-shot。

## 输入、决策与校验

1. 共用召回提供当前原文、同会话前文、主体、已有连接及四类记忆。基础候选包按 24,000 字节整理，程序随后从候选主体的可见别名和描述生成身份依据 B 列表，补入对应原文；当前 API 用户有专用依据。实际模型输入量单列记录。
2. 主体模型输出 `subjects` 与 `connections`。`reuse` 提供当前原文中的短提及及所选 B；`create`、`pending` 的 reference 为 null。别名和描述仍作为独立增量输出。
3. 程序核对本轮提及的 source_id、引文中的文字、身份 evidence、所选 B 与 target_id 的归属，以及历史来源的用户归属和时间可见性。现有主体 ID、kind 与当前用户身份规则继续检查。
4. 身份有效后，分别接收有来源的别名和描述；无效增量独立记录。主体决定沿用既有别名与描述。主体待定时，依赖它的连接和记忆保留待定。
5. 四类记忆模型读取固定主体视图和同批历史，提取 fact、preference、experience、event。程序编译追加计划、校验日期及来源，生成主体／记忆图边和检索文档。
6. 向量请求完成后，主体、连接、记忆、图、索引和应用检查点一起提交；原文与请求检查点事先保存。相同请求保持幂等，写入失败后复用已保存的模型输出。

程序负责结构与证据的一致性；回指含义是否足以指认某一身份，仍由模型结合上下文判断。多个身份同样合理时，模型使用 pending。原文与历史依据可追溯，并不等价于语义身份判断已经正确。

## 架构变更边界

| 部分 | 本版处理 |
| --- | --- |
| 主体模型 | 保留 individual（人或动物）、organization（组织／团队）、稳定 user，以及 create／reuse／pending |
| 名字与描述 | 保留 aliases／descriptions 及其来源；复用身份时分别校验增量 |
| 身份校验 | 增加当前 mention 与历史 B 依据的对应校验；退出当前引文必须完整复现旧名字／描述的门槛 |
| few-shot | 使用独立 JSON 资源中的 13 组英文输入输出；实际渲染器与真实调用一致；运行时沿用通用规则 |
| 主体连接 | 保留无向端点与来源；相同主体对合并来源；具体联系含义由四类记忆保存 |
| 完整实验入口 | 新增 `SubjectGraphEngine`、两个供应商适配器与 Golden runner，贯通 Add／Search |
| 记忆维护 | 保留两次正常调用与程序追加保存：主体一次、四类记忆提取一次；两个阶段共享至多一次协议修正 |
| 召回 | 沿用混合检索、名字／描述、参与者与一层连接；Search 的图种子来自实际查询命中及命中记忆参与者 |
| Search | 保留检索决策、冷热机制、时间可见性、Jev 重排与原文证据输出 |
| 存储 | 实验使用 MemoryStore 的六个逻辑集合并导出完整快照；新增物理数据库／表均为 0 |
| 生产与历史 | 生产 src 入口维持 V32；历史实验保留冻结代码和结果；本次修改保持未提交 |

完整实验入口负责主体新结构与生产记忆模型之间的适配。既有 HTTP 接口通过离线 TestClient 验证；Golden 直接调用同一公开 Add／Search 引擎合同，运行报告中单列执行方式。

## 两模型对照口径

两组使用同一冻结代码、原文与评分脚本，按时间顺序处理相同 159 条输入、13 道检索题及 4 条生命周期输入。DeepSeek 和 GPT 分别承担主体维护、四类记忆提取与 Search 决策；向量和 Jev 配置共用。两组从独立空的 MemoryStore 开始。

DeepSeek 使用官方 `deepseek-flash`、关闭 thinking、JSON object 模式；GPT 使用既有中转站的 `gpt-4o-mini`、原生 JSON Schema。任务提示、示例、程序校验与评分一致，供应商输出约束存在上述差别。请求的模型名称、物理调用与耗时由本地诊断记录；服务端实际版本随供应商别名解析。该实验比较当前两套可用配置下的整条链路表现，单次结果同时受生成与排序波动影响。

Golden 题目与答案仅进入评分侧；写入和检索提示接收原始用户输入及当前用户可见的历史记忆。运行时 few-shot 资源与评测 fixture 分离。159 条原文来自 Microsoft RHELM 的合成数据子集，完整输入与历史基线的 SHA 一致。

## 验证与完成标准

完整离线结果：378 passed，0 skipped，12.83 秒。覆盖回指词变化、依据归属、来源隔离、未来证据、待定消歧、主体到四类记忆再到检索、原子提交、失败续跑、快照恢复、幂等、一次共享修正及 HTTP 合同。

真实主体预检与完整 Golden 分别保存。Golden 验收要求：两组 163 个单元完成、13 题完整计分、3 次生命周期检索、全部原文排名复算一致、图与证据审计通过、冻结代码和输入保持一致。报告同时列出待定、身份拒绝与协议修正，检索成绩采用原文证据 Recall@K。

结果与已知语义限制见 [V35 两模型报告](../golden-v35-model-comparison.md)。
